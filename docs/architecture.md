# Архитектура этапа 1

Bootstrap.server — точка композиции. Shared не зависит от серверных сервисов; клиент не загружает код из ServerScriptService. Чистые FloorGenerator, FloorValidator, CombatRules, ProfileRules и RunRules исполняются также через Lune.

## Состояния забега

Hub → Loading → Active → Complete / Defeated → Loading → Hub. Ошибка подготовки возвращает в Hub. Вход в следующий production Place проходит только после успешного сохранения. В состоянии Loading сервер не принимает боевые действия, расход предметов или награды. CharacterAdded восстанавливает положение, но не отменяет поражение.

На сервере Preview каждому игроку назначается слот с отдельным смещением геометрии. В production SOLO получает собственный резервный сервер. Это прототип изоляции для SOLO; команды и CO-OP ещё отсутствуют.

## Генерация

Локальный PRNG с seed строит дерево уникальных клеток. Первые комнаты обеспечивают ловушку, бой и сокровищницу; выход выбирается среди дальних комнат. Валидатор проверяет размеры, уникальность координат, последовательные IDs, типы, границы, связи соседних клеток, дерево и достижимость выхода. RoomGenerator строит комнаты 32×32 через 48 studs; CorridorGenerator перекрывает 16-stud промежуток. Проходы имеют ширину 10 studs.

Пол ограничен Atomic-моделью для StreamingEnabled. Перед переносом игрока сервер запрашивает подгрузку позиции; окончательная проверка загрузки, физики и навигации выполняется в Roblox.

## Граница доверия

Клиент отправляет Action(name,payload). Сервер допускает пять известных действий, проверяет тип payload и token bucket на игрока/действие. Для Attack сервер сам выбирает ближайшую цель своего забега, проверяет дистанцию, направление, raycast, здоровье и cooldown. Шипы проверяют положение и пересечение на сервере. Сундук/выход требуют активного забега и близости. Клиент не назначает урон, награды, права или состояние профиля.

Движение персонажа использует стандартную Roblox-репликацию; серверные проверки расстояния сами по себе не предотвращают teleport/speed exploits. Это ограничение отмечено в приёмке, а не заявлено как решённая защита.

## Профиль и допуск

Один DataStore FortisProfiles_v1, ключ u:UserId. Запись содержит data и аренду lock с идентификатором сервера/сессии и сроком 120 секунд. Обновление через UpdateAsync, продление каждые 30 секунд. ProfileLease задаёт проверенные чистые преобразования записи. Маркер releasedBy позволяет безопасно повторить освобождение после неоднозначного ответа; новая аренда удаляет маркер. Запись новой версии не понижается. При потере блокировки дальнейшие действия с наградами закрываются. BindToClose пытается освободить все профили с ограниченным временем ожидания.

MemoryStoreHashMap FortisRunTickets_v1 — кратковременный допуск (180 секунд), а не база прогресса. HUB резервирует сервер, сохраняет UserId/seed/privateServerId и отправляет только runId. Dungeon сверяет источник, резервный сервер и атомарно помечает билет своим JobId и уникальным claimId попытки. RunTicket разрешает повтор callback только для этой попытки; новый допуск с использованным билетом закрыт, включая тот же JobId. Некорректный seed, будущая дата и истёкший срок отклоняются.

ProfileService сериализует загрузку и сохранение на игрока независимо от замены записи entries. Ожидающее автосохранение получает текущую запись после входа в критическую секцию. Studio и Preview используют только временные профили. HUB и Dungeon в опубликованной Experience используют общий DataStore.

Журнал наград в профиле хранит последние 128 идентификаторов серверных событий. Он подходит для событий текущего прототипа; для ProcessReceipt необходим отдельный долговечный механизм идемпотентности в следующем этапе. Монетизация ещё не реализована.
